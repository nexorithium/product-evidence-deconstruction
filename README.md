# Product Evidence Deconstruction

基于**可核验证据**的 AI 与交互产品逆向拆解 Skill。

它以产品截图、录屏、可访问网站、源代码或其他一手资料为依据，从 **用户层 → 技术层 → 模型层 → 数据层**分析产品行为，交付一份证据可追溯的独立 HTML 报告。内部实现不可见时，明确区分事实、推断、建议和未知。

本项目是一套供 Agent 使用的主指令、分析规范、界面配置和报告模板，不是独立运行的应用。主入口为 [SKILL.md](product-evidence-deconstruction/SKILL.md)。

## 这个 Skill 能做什么？

研究一个 AI 产品时，除了界面和最终结果，你可能还想知道：

- 用户完成任务经历了哪些步骤，在哪里选择、等待、修改或中断？
- 哪些 Agent 或组件实际参与处理，它们接收和输出什么？
- 工具、上下文、状态和下游交接如何关联？
- 哪些环节需要模型理解或生成，哪些实现仍无法确认？
- 能否根据一个 Agent 的可观察行为，编写功能等价的提示词？
- 每条结论有什么证据，哪些只是建议设计？

这个 Skill 将上述问题组织成可复核的分析过程，避免把猜测写成事实。

## 核心能力与分析模式

根据任务选择能够满足目标的最小模式，不默认展开所有内容。

| 模式 | 适用需求 | 主要交付内容 |
| --- | --- | --- |
| 用户旅程 | 分析用户如何完成任务 | 可观察步骤、选择、反馈、阻力、纠偏、失败与中断路径 |
| Agent 契约 | 分析实际出现的 Agent 及其协作 | Agent 清单、六类输入、可观察判断、工具、输出、全局上下文读写与下游交接 |
| 单 Agent 功能等价提示词 | 根据目标 Agent 的行为编写提示词 | 输入/输出与工具契约、状态机、System Prompt、规则—证据追溯表、最小测试集 |
| 完整产品架构 | 拆解产品的端到端系统关系 | 功能域、分层架构、上下文、知识与资产、模型、数据实体、基础能力、现状/建议与风险 |

### 1. 用户旅程拆解

从最早可见事件开始，还原用户目标、输入、产品响应、用户选择、处理结果和当前终点。除正常路径外，还检查有证据支持的修改、重新生成、用户确认、失败、中断和恢复。

```text
用户目标 → 输入 → 产品响应 → 用户选择 → 系统处理 → 结果反馈
                                    ↘ 纠偏 / 失败 / 中断 / 恢复
```

页面提供某个控件，不代表用户已经使用它；只有最终状态截图，也不一定足以还原完整旅程。

### 2. Agent 契约分析

根据可见名称、独立职责、代码定义、任务/运行对象或明确输出识别 Agent，不因产品类别或计划中的角色名称而补出 Agent 清单。

每个 Agent 的输入按六类来源检查：

1. 用户当前输入：需求、反馈、修改、确认、中断与上传材料。
2. 用户长期信息：可见的偏好、权限、套餐、资产与历史。
3. 项目全局上下文：配置、内容、当前状态、引用、确认与资产。
4. 上游 Agent 输出：字段、资产、启动前提与重跑关系。
5. 平台知识与资产：模板、专业知识、能力限制及相关规则。
6. 工具与运行时结果：成功、失败、中断、重试、状态写入与版本。

进一步记录触发条件、可观察判断、工具前后置条件、输出、上下文读写、完成条件和下游交接。公开计划摘要属于可观察行为，不是私有思维过程。

详见 [Agent 分析规范](product-evidence-deconstruction/references/agent-analysis.md)。

### 3. 单 Agent 功能等价提示词

在目标明确且证据足够时，推导可直接使用的功能等价 System Prompt，并交付状态机、规则追溯表及覆盖正常输入、缺少输入、局部修改、工具失败、中断和状态冲突的最小测试集。

**功能等价提示词不等于恢复了官方 System Prompt。** 未公开的原始提示词不得声称已经获取或还原；兼容可观察行为的规则与增强稳定性的建议规则也必须区分。

只要求 Agent 契约时，不继续编写完整提示词；只拆一个 Agent 时，不顺带扩展到其他 Agent。

### 4. 完整产品架构

结合用户流、Agent/控制流、工具流、上下文/数据流和资产流，分析全局上下文、知识与可复用资产、模型接入、数据实体及基础设施能力，并区分当前架构（As-Is）与建议架构（To-Be）。

内部选型不可见时，只描述所需能力、可能的实现类别、推荐属性和未知原因，不指定未经证实的数据库、消息队列、框架、语言、云服务或模型厂商。

详见 [架构分析规范](product-evidence-deconstruction/references/architecture-analysis.md)。

## 四层拆解框架

| 层级 | 回答的问题 |
| --- | --- |
| 用户层 | 用户想完成什么、做了什么、看到了什么、在哪里需要选择？ |
| 技术层 | 哪个组件或 Agent 处理、使用什么工具或服务、状态如何变化？ |
| 模型层 | 需要哪些理解或生成能力、有哪些限制与校验、路由机制有什么证据？ |
| 数据层 | 读取和写入哪些输入、资产、引用、版本、确认、错误与权限？ |

四层不是四份互不关联的清单。每个关键事件应保留纵向追溯关系：

```text
用户行为 / 页面反馈
        ↓
组件或 Agent / 工具 / 状态变化
        ↓
模型能力 / 约束 / 校验
        ↓
数据读取 / 写入 / 资产与版本
```

详见 [四层拆解框架](product-evidence-deconstruction/references/four-layer-framework.md)。

## Evidence First：证据优先

形成产品结论前，至少取得一种可检查的一手证据：

- 足够完整的产品截图或录屏；
- 可正常访问的产品网址；
- 源代码或导出的项目文件；
- 其他包含可观察界面、状态和结果的一手材料。

只有宣传页、口头描述或未经验证的二手总结，不足以直接完成拆解。官方资料可以支持其明确公开的结论，但不能自动补齐未展示的行为或实现。

最低证据随分析深度变化：用户旅程需要连贯的输入、选择、反馈和终点；Agent 契约需要可观察身份或职责及输入、判断、结果和交接；提示词与完整架构需要更完整的任务记录。

证据不足时，盘点已有材料、说明结论边界、请求最小必要补充材料，并停在证据计划或范围明确的部分报告。不得用经验补写缺失步骤。

### 结论分类

| 标记 | 含义 |
| --- | --- |
| **【已确认】** | 页面、代码、官方资料或可复核结果直接支持 |
| **【合理推断】** | 多条已确认观察共同支持，但内部实现不可见 |
| **【建议设计】** | 为解决风险或缺口提出的改进，不是当前产品事实 |
| **【未知】** | 现有证据不足以判断 |

为证据分配稳定编号，并在结论、规则、表格和图中引用。以下为说明性示例：

> E02 显示规划摘要，E03 显示搜索结果，因此可以确认规划摘要与搜索结果均可见；是否由独立 Planner Agent 执行，目前未知。

界面有字段，不代表 Agent 已读取它；展示计划，不代表工具已经执行。工具执行需要结果、资产或状态变化等证据支持。

详见 [证据协议](product-evidence-deconstruction/references/evidence-protocol.md)。

## 工作流程

```text
盘点证据并编号
      ↓
划定查看范围与证据边界
      ↓
判断产品类型与分析重心
      ↓
还原时间顺序
      ↓
用户层 → 技术层 → 模型层 → 数据层
      ↓
检查状态冲突
      ↓
形成目标交付物与证据映射
      ↓
生成并验证独立 HTML 报告
```

### 产品类型路由

现有规范覆盖生成式创作工具、通用执行 Agent、对话或陪伴产品、Copilot 或编辑器，以及企业工作流产品。可选择一个主要类型和多个次要类型，并说明分类证据及由此调整的分析重点。

例如，创作工具重点检查参考资料、生成阶段、资产版本与一致性；执行 Agent 重点检查授权、工具行动、验证闭环与完成标准。聊天界面本身不足以证明产品属于 Agent 类型。

详见 [产品类型路由](product-evidence-deconstruction/references/product-types.md)。

### 状态冲突检查

聊天中的“已完成”声明不等于完成证据。需对比任务状态、工作区或画布资产、资产库、历史版本、预览/播放/导出可用性，以及错误或不完整提示。

如果聊天声称完成，但资产缺失或预览不可用，应同时记录各方信号；没有权威事实源时，不自行选择一个作为真相。完成判断还需核验必要资产、状态写入、结果校验和用户确认。

## 现场检查与安全边界

现场产品检查默认只读。可以打开已有记录、滚动、展开公开计划摘要、切换只读分类或打开已有预览。

未经用户明确授权，不触发生成或重新生成、发送消息、发布、删除、购买、充值、权限变更或资产覆盖。不得查看或输出密码、Cookie、Token、鉴权头、浏览器存储或其他私密凭证。

遇到登录、双重验证、验证码或需要用户接管时，暂停并请用户完成。

## HTML 报告

完成的拆解以用户授权工作区中的独立 `.html` 文件交付。报告通常包含：

- 执行摘要、查看范围、证据来源与缺口；
- 产品分类与当前模式的专项分析；
- 四层分析与跨层追溯关系；
- 状态冲突、风险与建议设计；
- 规则或组件—证据追溯表；
- 未知问题与最值得继续验证的事项。

根据需要使用表格、Mermaid、HTML/CSS 或 SVG 图；关键节点标注证据编号，图中包含证据等级与线型图例。

默认采用浅色、高对比主题，适配手机、桌面与打印。报告基于模板改写，交付前检查 HTML 语法、占位符、空章节和本地证据链接；除非确有必要且已获允许，不依赖外部网络资源。

详见 [HTML 交付规范](product-evidence-deconstruction/references/html-delivery.md) 和 [报告模板](product-evidence-deconstruction/assets/report-template.html)。

## 使用示例

在支持并已加载该 Skill 的 Agent 环境中，提供明确目标及可核验证据。下面是任务示例；仓库未提供独立安装脚本或命令行程序。

### 用户旅程与 Agent 契约

```text
使用 $product-evidence-deconstruction 拆解这个 AI 产品。

目标：分析它的用户旅程和 Agent 契约。
证据：产品网址、按时间顺序整理的操作录屏和页面截图。
重点：Agent 分工、工具调用、上下文读写、状态变化和用户确认节点。

只记录实际出现且有证据支持的 Agent。
无法确认的部分标记为【未知】，最终交付证据可追溯的 HTML 报告。
```

### 单 Agent 功能等价提示词

```text
使用 $product-evidence-deconstruction 分析我指定的目标 Agent。

我会提供目标 Agent 的名称，以及本次任务中完整的可观察记录。
请分析输入、可观察判断、工具、输出、上下文和下游边界，
并编写功能等价 System Prompt、状态机、规则—证据追溯表和最小测试集。

区分已确认、合理推断、建议设计和未知。
不要声称还原官方提示词；证据不足时说明需要补充什么。
```

## 适合谁？

- **AI 产品经理**：竞品分析、用户旅程、Agent 工作流与产品架构研究。
- **AI Builder 与独立开发者**：理解产品行为，研究工具、上下文、状态和交接设计。
- **AI 研究者**：研究 Agent 行为、工具使用、人工确认与产品化系统。

## 参与改进

可以围绕证据协议、Agent 契约、架构分析、上下文设计、功能等价提示词、报告可视化和产品类型路由提出改进。新增规则或示例时，应明确证据来源及适用边界，保持主入口、参考规范和模板一致。

## 核心理念

根据可以验证的产品行为，尽可能准确地理解产品如何工作。

```text
Evidence > Guess
Behavior > Marketing
Unknown > Hallucination
Traceability > Confidence
```

Evidence-driven reverse engineering for AI products and Agents.
