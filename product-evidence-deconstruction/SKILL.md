# 产品证据拆解

在不预设内部实现的前提下，完成可复用、证据驱动的产品拆解。先识别产品类型，再从用户层逐步下钻到技术层、模型层和数据层，最终交付独立 HTML 文件。

## 强制证据门槛

形成产品结论前，必须至少取得一种可以检查的一手证据：

- 足够完整的产品截图或录屏；
- 可正常访问的产品网址；
- 源代码或导出的项目文件；
- 其他包含可观察界面、状态和结果的一手材料。

只有宣传页、口头描述或未经验证的二手总结时，不足以直接完成拆解。

当证据无法支持用户要求的拆解深度时：

1. 盘点当前已有证据；
2. 说明它能支持和不能支持哪些结论；
3. 请求最小必要补充材料；
4. 停在证据计划或边界清晰的部分报告。

不得用产品常识或个人经验悄悄补全证据缺口。

## 证据与安全规则

- 除非用户明确授权修改，否则现场产品检查默认只读。
- 不得为了取证而发送消息、生成或重新生成内容、发布、删除、购买、充值、修改权限或覆盖资产。
- 不得查看或输出密码、Cookie、Token、鉴权头、浏览器存储或其他私密凭证。
- 页面公开的规划或判断摘要属于可观察行为，不是隐藏思维链，也不是官方提示词原文。
- Agent 声称工作完成不等于完成证据。必须核验实际资产、状态、历史、预览或工具结果。
- 只有页面、代码或官方资料明确展示时，才能使用官方工具名；否则使用 `<生成视频>` 这类语义化占位名，并标注“功能命名，并非官方工具名”。
- 每条结论必须标记为：
  - **【已确认】**：页面、代码、官方资料或可复核结果直接支持。
  - **【合理推断】**：为解释多条已确认行为所需，但内部实现不可见。
  - **【建议设计】**：用于解决风险或缺口的改进方案，不是当前产品事实。
  - **【未知】**：现有证据无法判断。

开始收集或解释证据前，阅读 [证据协议](references/evidence-protocol.md)。

## 先判断产品类型，再决定拆解重心

识别产品的主要类型和可选的次要类型，不要把所有产品都硬套成 Agent 或 AIGC 产品。

常见类型包括生成式创作工具、通用执行 Agent、对话或陪伴产品、Copilot/编辑器、企业工作流产品。

阅读 [产品类型路由](references/product-types.md)，选择适用的取证重点。在报告中写明产品分类及其证据。

## 选择本轮拆解模式

使用能满足当前目标的最小模式：

1. **用户旅程**：可观察步骤、选择、反馈、情绪、阻力、纠偏、失败和中断路径。
2. **Agent 契约**：实际 Agent 清单、六类输入、可观察判断、工具、输出、全局上下文读写和下游交接。
3. **单 Agent 功能等价提示词**：基于证据推导行为规则、状态机、工具契约、提示词、追溯表和测试集；不得声称还原官方原文。
4. **完整产品架构**：功能域、端到端流程、分层架构、上下文、知识、模型、数据实体、基础能力、现状/建议和风险。

只读取当前模式需要的详细规范：

- Agent 契约或单 Agent 提示词：阅读 [Agent 分析规范](references/agent-analysis.md)。
- 完整产品架构：阅读 [架构分析规范](references/architecture-analysis.md)。
- 所有模式：阅读 [四层拆解框架](references/four-layer-framework.md)。

## 核心流程

1. **盘点证据**
   - 分配稳定证据编号。
   - 记录来源类型、时间顺序、页面原文、控件、资产、状态、错误和访问限制。
   - 区分用户输入与产品生成内容。
2. **划定证据边界**
   - 说明查看范围和无法访问的内容。
   - 识别缺失的时间线、隐藏状态、历史版本、未播放媒体或登录阻塞。
3. **判断产品类型**
   - 确定主要类型和次要类型。
   - 解释分类如何改变拆解重心。
4. **还原时间顺序**
   - 从最早可见事件开始。
   - 追踪：触发者 → 处理者 → 判断 → 工具/结果 → 状态写入 → 用户确认 → 下游交接。
   - 纠偏、失败、中断和恢复只有在有证据时才能写为现状，否则标为未知。
5. **依次分析四层**
   - 用户层 → 技术层 → 模型层 → 数据层。
   - 保留跨层关联，使每个关键界面步骤都能追溯到处理逻辑、模型能力和数据/状态。
6. **检查状态冲突**
   - 对比聊天声明、画布或工作区资产、任务状态、历史、预览和资产库。
   - 冲突时同时记录各方信号；没有权威事实源时不得自行选择一个作为真相。
7. **形成目标交付物**
   - 在节点、规则、表格和图中标注证据编号。
   - 严格区分当前事实、合理推断和建议设计。
8. **生成并验证 HTML**
   - 阅读 [HTML 交付规范](references/html-delivery.md)。
   - 复制并改写 [HTML 报告模板](assets/report-template.html)。
   - 在用户授权的工作区写入独立 `.html` 文件。
   - 校验 HTML 语法，并确认模板占位符已全部替换。

## 四层贯穿原则

每份完成的拆解都必须让读者回答：

- **用户层**：用户想完成什么、做了什么、看到了什么、在哪里需要选择？
- **技术层**：哪个产品组件或 Agent 处理、使用了什么工具/服务、状态如何变化？
- **模型层**：需要什么理解或生成能力、有哪些约束与校验、路由机制还有哪些未知？
- **数据层**：读取或写入了哪些输入、资产、引用、版本、确认、错误和权限？

不得把四层写成互不关联的四份清单。关键事件必须能够纵向贯穿四层。

## 输出要求

- 最终交付完整、可读的 HTML；用户没有指定时使用浅色高对比主题。
- 开头包含执行摘要、查看范围、证据来源、证据缺口和产品分类。
- 精确映射优先使用表格；状态、时序、数据流和架构关系在确实有帮助时使用 Mermaid、HTML/CSS 或 SVG 图。
- 图中必须包含证据等级和线型图例。
- 关键结论和节点旁标注证据编号。
- 结尾列出未知问题和最值得继续验证的事项。
- 只做到用户要求的深度。用户只要 Agent 契约时，不得继续写完整提示词；只拆一个 Agent 时，不得顺带拆其他 Agent。
